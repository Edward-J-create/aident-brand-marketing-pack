# Online Document Delivery

The default final artifact is **one native, editable online document plus a durable original-file library when media exist**, created through Aident Loadout. Local Markdown is an intermediate drafting buffer/backup, never a successful default handoff. Use the user's explicit provider if given. Otherwise select a connected provider whose document and original-file actions can handle the actual files in this run; prefer the source provider when suitable. Do not keep retrying a provider already shown to lack write permission. Never create three redundant documents merely because three actions exist.

## Provider workflow

1. Discover exact document-create, image-insert, durable file-upload, and read-back actions in Aident Loadout (`capabilities search`); inspect their live schemas (`capabilities get`) and current connection (`whoami` and `vault status`, or matching host tools). Do this before the full drafting pass and compare real file types/sizes with provider limits. **Connected/readable does not prove writable**; document creation, image insertion, and file storage can have different permissions. A connection installed after an earlier check requires a fresh Vault read.
2. Prepare Markdown for the [output template](output-template.md) and an original-file placement plan. For Lark, Google Docs, or Notion, check whether tables, links, images, and any attachment blocks survive conversion. Respect parent/location and audience access requirements. An inline image's displayed size is not evidence that the original file was preserved; retain and verify the original separately.
3. Create **one** master document with a brand-specific title. If the action returns `requires-user-acknowledgement`, request explicit approval for this exact write; only then retry the identical action/input with the one-time acknowledgement scope. Never self-acknowledge or request an indefinite scope merely to make delivery automatic. Record the returned document/page ID and URL. A local file path does not satisfy this step.
4. Upload each permitted original to durable companion storage using a compatible connected action. Verify file identity and intended-audience access; do not use a temporary transfer URL as the final location. Insert high-quality display images and video posters/player blocks where supported, each with a direct path to its original. If an insertion fails, try a provider-supported repair or ask for a compatible destination. Do not silently replace a promised original with a thumbnail or generic page link.
5. Read the document back with the matching provider action. Verify title; requested locale headings; representative copy; source links; actual image/video placements; labels and original-file links; and the asset index. Reopen a sample of original files, including at least one image and one video when present. If conversion strips a table or media object, repair and read back again.
6. Report both the document URL and original-file library location, plus verified/rights-blocked/missing counts. If the user must grant access, say so. Do not assert the document or files are editable by others unless sharing permissions were checked.

## Media in the document

- Existing approved image: preserve the original image or vector file in companion storage; insert the original-compatible image or a clearly labeled high-quality display rendition into the document. If embedding is unsupported, show the direct persistent **original-file** link and label the display gap. A source page or small thumbnail is not an adequate replacement.
- Existing approved video: preserve the original master/export in companion storage. Embed it if supported; otherwise include a poster, duration/format, and a direct persistent link to the original file. A streaming playlist is a reference, not an original video deliverable. Never claim an embedded player that was not verified.
- Missing visual/video: use a clearly styled concept/brief card with status `Missing` or `Proposed`; no synthetic placeholder masquerading as a rendered asset.
- If the source is a private file and the destination's audience cannot access it, the item remains blocked for sharing. Do not publish a private URL as if public.

## Failure recovery

If a create or upload action fails, diagnose schema, account, app scopes, permission, parent location, file limits, and content conversion once. A Lark `app_scope_not_applied` error names an **application-level** permission: the app developer/administrator must grant the stated scopes. Browser login, local CLI user login, and Aident Vault `connected` do not themselves repair that bot-app permission. Do not retry the identical failing action without a changed permission state. If the user did not mandate Lark, try a fresh Vault check and one connected Google Docs or Notion route that supports both document and actual files. Do not silently switch from an explicitly requested provider. Preserve the local draft and permitted originals, but say **online delivery incomplete** or **original-file delivery incomplete** as applicable; name the exact blocker and request the required connection or destination choice. If create succeeds but read-back or original-file verification fails, share the link as unverified and do not label the pack ready. Never paste credentials or private document contents into logs.
